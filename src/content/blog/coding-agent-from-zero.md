## Coding Agent是什么？

<strong>先了解Agent是什么</strong>

你可以理解为 Agent（智能体） = LLM（大脑） + Tools（身体）

对于大语言模型（LLM），只可以输出文字，无法帮你做一些工作。所以相当于一个大脑，只可以思考，却无法行动。

而加上Tools，便可以让LLM调用Tools来实现一些操作，例如可以调用read来看文件，调用write工具来写文件。

对于单次调用，似乎只是调用一下工具，也没什么特别的，但是如果将上次调用的结果作为下次的输入，并可以进行多次此操作，最后自行决定什么时候结束，便形成了自主思考的效果，<strong>可以自主思考，可以自主行动，这便是Agent（智能体）</strong>。

举个例子，我们有两个tool，一个是read，一个是write，如果可以调用read看代码，然后把看的结果记住，然后调用write写代码，写之后，再次调用read检查代码，如果有不对的地方再次调用write，如此反复，直到最后满意才结束，这便是一个我们的写代码的助手，而不是简单的用于问答的搜索引擎。

<strong>Coding Agent是什么？</strong>

相信你肯定听说过，xx在coding，coding就是编码的意思，起这个名字说明这个人很喜欢写代码。

那Coding Agent也很明显，就是编程智能体，即用于写代码的Agent。

即你用自然语言告诉它需求，它能读取代码、修改文件、执行命令和运行测试，帮助完成开发任务。

## Coding Agent要实现哪些功能？

- <strong>Agent 执行循环</strong>：接收用户任务，调用模型，执行模型选择的工具，将工具结果反馈给模型，持续推进直到完成或停止。
- <strong>工具系统：</strong>定义工具及参数；支持读取文件、搜索代码、修改文件、执行命令；返回执行结果和错误信息
- <strong>安全控制</strong>：限制文件访问范围和命令执行权限；对危险操作进行确认；设置执行超时和最大循环次数
- <strong>Token 统计与过程展示</strong>：统计输入、输出和累计 Token；展示模型调用、工具调用、执行状态及错误
- <strong>Session 管理</strong>：创建、保存、读取和恢复会话；持久化消息、工具调用结果和任务进度，支持跨次运行继续任务
- <strong>Provider 抽象</strong>：统一模型服务的调用接口；支持切换服务商和模型；适配响应格式、用量信息与错误处理
- <strong>流式交互</strong>：通过 SSE 增量接收输出；拼接工具参数分片；参数完整后执行工具；实时渲染 Markdown
- <strong>上下文管理</strong>：控制上下文预算；压缩历史并保留目标、关键决策和进度；切分时保持工具调用与结果完整对应
- <strong>记忆系统</strong>：跨会话保存项目约定和知识；按当前任务读取相关记忆；新增、更新和修正已有记忆
- <strong>Subagent 协作</strong>：委派子任务；传递必要上下文；并行调度和跟踪状态；汇总结果并处理子任务失败
- <strong>运行分析与诊断</strong>：展示 Session 时间线和 Agent 执行图；分析耗时、Token 消耗及重复操作；定位失败步骤和原因

## 实战：开发计划

> 本次实现的是CLI Coding Agnet。

### Day 1～Day 7：搭建一个基础可用的 Coding Agent

#### Day1：打通第一次模型调用

<strong>任务</strong>：定义请求、消息、响应和错误结构，实现一次非流式 HTTP 模型调用，处理配置读取、鉴权与基础错误。

<strong>验收</strong>：用户输入一段文字，能返回模型回答。

#### Day2：让模型认识工具

<strong>任务</strong>：定义工具名称、描述和 JSON Schema，将工具声明发送给模型。解析模型返回的工具调用，保留调用 ID、名称和参数，校验参数 JSON，并区分文本回答与工具调用。

<strong>验收</strong>：程序能正确识别模型想调用什么工具、传入什么参数，非法参数能被明确拒绝，本阶段暂不执行工具。

#### Day3：实现 Agent Loop

<strong>任务</strong>：实现“调用模型 → 执行工具 → 回传结果 → 再次调用模型”的循环，管理消息历史，支持多轮工具调用、工具错误反馈和最终回答，并设置基础轮数上限。

<strong>验收</strong>：Agent 能根据工具结果继续判断和执行，直到给出最终回答；达到轮数上限后停止调用工具并尝试总结。

#### Day4：实现四个内置工具

<strong>任务</strong>：实现 bash、read、write、edit，让 Agent 能执行命令、读取文件、创建文件和修改内容。建立统一工具接口与注册表，根据工具名称分发调用，统一处理成功和失败结果。

<strong>验收</strong>：Agent 能读取本地代码、修改文件并执行测试命令；工具执行结果和错误能够正确回传模型。

#### Day5：建立系统 Prompt 与交互式 CLI

<strong>任务</strong>：编写系统 Prompt，明确 Agent 身份、工作区和工具规则，要求先读后改、修改后验证。实现 CLI 连续输入、多行编辑和退出机制，在同一会话中保留消息历史。

<strong>验收</strong>：用户可以连续对话，后续任务能引用前面的分析和工具结果，单轮失败后仍可继续输入。

#### Day6：加入资源限制与执行审批

<strong>任务</strong>：限制工具输出大小、任务轮数和执行时间。执行 bash、write、edit 前展示调用并请求确认，将用户拒绝作为工具结果回传模型，支持 --yes 自动批准。

<strong>验收</strong>：工具输出过大时会截断并提示，任务超时或达到轮数上限时会停止；未经批准的命令和文件修改不会执行。

#### Day7：支持中断与取消

<strong>任务</strong>：通过 Go context 贯穿模型请求和工具执行，处理 Ctrl+C、超时和退出。取消 HTTP 请求及命令进程，回滚未配对的消息，释放资源并恢复终端状态。

<strong>验收</strong>：Ctrl+C 能退出会话并停止底层操作，不再执行后续工具；用户取消、任务超时和普通失败有明确区分。

### Day 8：让 Agent 的执行过程可见

#### Day8：Token 统计与过程可视化

<strong>任务</strong>：展示模型轮次、当前工具、执行状态和耗时。按任务累计模型调用次数、工具调用次数及模型服务返回的 Token 用量，明确标记缺失或部分统计。

<strong>验收</strong>：任务结束后能查看耗时和用量汇总；缺失 usage 时显示不可用，非交互模式的统计不会混入最终回答。

### Day 9～Day 10：支持会话持久化与模型切换

#### Day9：保存与恢复 Session

<strong>任务</strong>：为会话生成 ID，将消息、工具调用、工具结果和任务状态保存为版本化 JSON，采用原子写入。支持通过 --session 恢复，并校验会话 ID、版本、工作区和消息配对。

<strong>验收</strong>：关闭程序后，可以在同一工作区恢复会话并继续对话；损坏或不匹配的存档会明确报错。

#### Day10：抽象模型 Provider

<strong>任务</strong>：让 Agent 依赖统一的 Provider 接口，定义公共请求、响应、错误及可选流式接口。通过配置工厂创建模型适配器，使用 Fake Provider 测试 Agent 行为。

<strong>验收</strong>：现有 OpenAI 兼容服务通过统一接口运行，新增适配器无需修改 Agent Loop 和工具系统，核心流程可以脱离真实模型进行测试。

### Day 11～Day 12：实现完整的流式交互

#### Day11：接入 SSE 流式响应

<strong>任务</strong>：发送流式请求，解析文本增量、工具调用增量、结束事件和用量事件，将文本增量传递给 CLI。处理 HTTP 错误、断线、异常结束、超时和取消。

<strong>验收</strong>：模型生成文字时，终端能即时展示；流异常结束时不会保存半截回复，也不会执行未完成回复中的工具。

#### Day12：完善工具分片与流式 Markdown

<strong>任务</strong>：按调用索引累积工具名称和参数，支持多个调用交错返回，流正常结束并校验完整后再审批和执行。实时渲染 Markdown，处理未闭合格式、高频增量、长文本、窗口变化和渲染失败。

<strong>验收</strong>：工具参数跨分片时能正确拼接；标题、列表和代码块在生成过程中保持可读，结束后排版完整，退出时正确恢复终端。

### Day 13～Day 14：让 Agent 能够处理长任务

#### Day13：实现上下文预算与摘要压缩

<strong>任务</strong>：在模型请求前检查上下文预算，保留最近约 20k Token 的完整消息，将较早历史生成滚动摘要。统一手动压缩、自动压缩和上下文超限恢复，独立保存完整原文与压缩检查点。

<strong>验收</strong>：长对话能通过“摘要＋近期原文”继续执行；压缩失败时保留原历史，超限恢复不会重放已经执行的工具。

#### Day14：保证压缩合法并验证信息保留

<strong>任务</strong>：按完整消息和工具批次选择保留边界，校验角色、参数 JSON 以及工具调用与结果配对。测试连续压缩、保存恢复，并用真实模型验证任务目标、用户约束、关键路径和最新测试状态的保留情况。

<strong>验收</strong>：压缩后的请求结构合法；连续压缩和恢复后仍能准确继续任务，遗漏目标、约束反转和过时测试状态等负例能够被验收识别。

### Day 15：为 Agent 建立项目记忆

#### Day15：加入跨会话项目记忆

<strong>任务</strong>：使用 `Agents.md` 保存关键约定和专题目录，将详情放在独立 Markdown 文件中，由模型按任务读取。通过普通对话和现有文件工具维护记忆，只在用户明确要求时保存、更新或删除。

<strong>验收</strong>：新会话能够复用项目知识；真实模型能选择相关专题，正确处理冲突、重复和删除，不把已删除内容重新写回。记忆维护不新增专用命令。

### Day 16～Day 17：引入 Subagent 与并行协作

#### Day16：实现一次 Subagent 委派

<strong>任务</strong>：注册 delegate_task，为子 Agent 提供任务目标、必要背景、相关项目记忆和独立消息历史。首版只开放 read，委派深度固定为一层，子任务继承父任务的取消和剩余时限。

<strong>验收</strong>：主 Agent 能委派模块分析，接收结论、文件位置、依据和执行状态，再继续完成任务；父子上下文互不混入，子任务失败能正常回传。

#### Day17：支持多个 Subagent 并行执行

<strong>任务</strong>：建立子任务管理器，控制并发与排队，收集成功和失败结果。统一取消、父子任务调用预算、CLI 状态展示及用量统计，保存父子关联和已完成结果，恢复时将未完成子任务标记为已中断。

<strong>验收</strong>：多个独立分析任务可以并行完成且不超过并发上限；部分失败不阻断其他任务，Ctrl+C 能统一停止，统计不重复累计，恢复后能查看已完成结果。

### Day 18：Langfuse观测Agent 的执行过程与失败原因

#### Day18：Langfuse观测Agent 的执行过程与失败原因

<strong>任务</strong>：在现有 Langfuse / OpenTelemetry 基础追踪上关联 Session、主 Agent、Subagent、模型请求和工具调用。展示时间线与执行图，分析耗时、Token、可用的成本数据、重复读取和连续失败，将典型失败补充为回归用例。

<strong>验收</strong>：跨进程恢复后的任务能归入同一会话，并展示父子 Agent 的完整调用关系；能够定位慢步骤和失败原因，追踪服务不可用时不阻断任务，缺失用量或价格时明确标记不可用或部分统计。
